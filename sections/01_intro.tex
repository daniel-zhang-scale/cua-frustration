\section{Introduction}
\label{sec:intro}

Computer-use agents (CUAs) operate graphical interfaces the way people do: they read the screen and act through the mouse and keyboard. In two years they have moved from research previews \citep{anthropic2024computeruse} to products \citep{openai2025cua,google2025geminicomputeruse} and open models \citep{qin2025uitars,wang2025uitars2,wang2025opencua}. Their progress is tracked by benchmarks such as OSWorld \citep{xie2024osworld}, on which the best agent completed 12.24\% of tasks at release against 72.36\% for people. In a standardized evaluation, frontier agents now score up to 91.6\% on the same benchmark \citep{aggarwal2026cuaspeedrun}, well above that human baseline.

These benchmarks ask one question of each run: is the final state correct? A deterministic checker or a rubric compares the end state with the goal \citep{xie2024osworld,zhou2024webarena,rawles2025androidworld,xue2025illusion}, and the agent may use a fixed budget of steps (15 to 100 on OSWorld) with no limit on time. Under this protocol, a correct run counts the same whether it takes five seconds or five minutes. Measurements of agent efficiency show what this hides. On OSWorld, the best agents take 2.7--4.3$\times$ more steps than a person needs, with end-to-end latencies of tens of minutes on tasks that take people a few minutes \citep{abhyankar2026osworldhuman}; on short UI-component tasks, even the fastest agent configuration takes 3.7$\times$ as long as a person \citep{guan2026componentbench}.

A user experiences such a run differently. A person who hands a task to an agent compares the agent with doing the task themselves, and stops the agent once it takes longer, or flails more, than they are willing to watch. HCI research has long studied this experience as frustration. In diary studies, users lost between a third and a half of their time at the computer to frustrating episodes \citep{ceaparu2004frustration,lazar2006severity}; delays beyond about ten seconds break a user's attention on the task \citep{miller1968response,nielsen1993usability}; and people stop relying on an automated aid once they have seen it err \citep{parasuraman1997humans,dietvorst2015algorithm}. Studies of today's agents report the same experience: latency is the main complaint and a reason users take over control \citep{mozannar2025magentic}, and deployed agents loop and finish more slowly than the user would by hand \citep{shome2026johnny}. For a user, a run they would have abandoned is a failed run, even if the agent would eventually have reached the goal.

The tasks most likely to exhaust a user's patience are often the ones people find easiest. Dragging a file, choosing from a hover menu, picking a date in a custom widget or closing a pop-up takes a person seconds, but it requires precise grounding, timing or continuous control, which agents still handle poorly \citep{li2025screenspotpro,zhang2025popups,guan2026componentbench}. This is Moravec's paradox \citep{moravec1988mind} in the graphical interface. Most benchmarks emphasize long workflows across applications \citep{xie2024osworld,xu2024theagentcompany,yuan2026osworld2}, in which such interactions are a small part of each task and their cost disappears into a single pass/fail verdict. Benchmarks that measure efficiency compare agents with the steps or time a person needs \citep{abhyankar2026osworldhuman,guan2026componentbench,arcprize2026arcagi3}, but none asks how much more than their own effort people would accept from an agent before giving up on it.

We introduce \bench, a benchmark that measures frustration rather than correctness alone (Figure~\ref{fig:teaser}). It contains 75 human-written tasks that people complete quickly (median \tbd{XX}\,s) and that centre on interactions prone to agent failure, in \tbd{eight} categories from continuous manipulation to interrupting dialogs (Table~\ref{tab:categories}). For each task, \tbd{n} annotators record two labels. \emph{Human effort} is the time and number of actions the task takes them. \emph{Human tolerance} is how long, and through how many unproductive actions, they would watch an agent before stopping it and doing the task themselves. A run succeeds only if the checker accepts the end state \emph{and} the agent stays within both tolerance budgets. Everything else counts as frustration: an outright failure, a loop, a run stalled on deliberation, and a correct run that finishes after the user would have taken over. A taxonomy of eight frustration patterns, with automatic detectors, explains why each frustrated run failed (Table~\ref{tab:patterns}).

We evaluate \tbd{M} frontier models (\S\ref{sec:experiments}). \tbd{Three findings, to be confirmed against results.} First, correctness overstates usability: the best model is correct on \tbd{XX}\% of runs but succeeds within human tolerance on only \tbd{XX}\%, while human annotators reach \tbd{XX}\%. Second, agents remain far from human effort even when they succeed, taking a median \tbd{X.X}$\times$ the human time on correct runs, and ranking models by tolerated success instead of correctness \tbd{reorders N of the M models}. Third, frustration concentrates in a few patterns: \tbd{looping and primitive failures account for XX\% of frustrated runs}, and \tbd{higher reasoning effort raises correctness but lowers tolerated success}.

Our contributions are:
\begin{itemize}\setlength\itemsep{0pt}
\item \textbf{\bench}, 75 human-written computer-use tasks that are easy for people, each with a deterministic checker and with human effort and tolerance labels from \tbd{n} annotators (\S\ref{sec:tasks}--\ref{sec:labels}).
\item \textbf{A tolerance-aware evaluation protocol} that turns human patience into a pass/fail criterion, with the tolerated success rate, the frustration rate and the tolerance gap between correctness and tolerated success (\S\ref{sec:metrics}).
\item \textbf{A taxonomy of frustration patterns} with automatic detectors validated against human labels (\S\ref{sec:patterns}).
\item \textbf{An evaluation of \tbd{M} frontier CUAs} showing that \tbd{headline finding} (\S\ref{sec:experiments}).
\end{itemize}
